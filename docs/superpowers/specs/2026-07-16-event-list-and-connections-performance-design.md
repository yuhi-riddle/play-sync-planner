# イベント一覧・つながり性能改善 設計

## 目的

次の3点をまとめて直す。

- イベント一覧で全履歴と関連データをアプリへ転送しない
- ブロック登録と関係削除を一つのトランザクションで実行する
- ブロック中ユーザーの表示名取得で、人数分の管理APIを呼ばない

一覧の表示内容と状態判定は変えない。新しい集計列は追加せず、既存データをそのまま使う。

## 採用方針

PostgreSQLのRPCへ、一覧の絞り込み・並べ替え・件数計算とブロック更新を移す。

イベント一覧RPCは、表示対象のイベントID配列と総件数だけを返す。アプリは返された10〜50件のIDを使い、カード表示に必要なイベント・日程調整・参加者だけを追加取得する。これにより、カード表示のTypeScriptロジックは残しつつ、全履歴の転送をなくす。

ブロックRPCは、ブロック登録、相互フォロー削除、双方のお気に入り削除を同じDBトランザクション内で実行する。どれか一つでも失敗した場合は、すべて元に戻す。

## データの流れ

### イベント一覧

1. `/events` が状態、カテゴリ、表示順、ページ、表示件数を受け取る。
2. 認証済みSupabaseクライアントから `list_owned_event_ids` RPCを呼ぶ。
3. RPCは `auth.uid()` が所有するイベントだけを対象に、現在のTypeScript実装と同じ規則で状態を計算する。
4. RPCは並び順を保った `event_ids` と `total_count` を1行で返す。対象ページが範囲外でも、空配列と正しい総件数を返す。
5. アプリは対象IDに限ってカード用データを取得し、RPCのID順に並べ直す。
6. 既存のページ補正、カード表示、清算表示、次の対応表示を使う。

RPCの状態判定は次の規則に合わせる。

- `done`、`cancelled`、`skipped` は日程終了済み
- それ以外は、`cancelled`、`skipped` ではない日程調整がすべて終了したときだけ日程終了済み
- 有効な日程調整がなければ、イベントの終了日または開始日で判定
- 終日予定は日本時間の23:59:59.999まで進行中
- 清算状態は `settling`、`needed`、`not_started`、`settled`、`not_needed` の優先順で集約
- 中止イベントの `not_started` は `not_needed` として扱う
- 対応中は「日程が未終了、または清算が未終了」
- 完了は「中止以外で、日程と清算が両方終了」
- 中止はイベント状態が `cancelled`
- 開催日順は、今後いちばん近い確定日時、なければ最後の確定日時、どちらもなければイベント開始日を使う

### ブロック

1. `blockUserAction` はログイン状態と対象UUIDを確認する。
2. 認証済みSupabaseクライアントから `block_user_atomic` RPCを呼ぶ。
3. RPCは自分自身ではないこと、共通イベントがあることを確認する。
4. ブロック登録、双方向のフォロー削除、双方向のお気に入り削除を一つのトランザクションで実行する。
5. 成功時だけ `/connections` を再検証する。

### ブロック中ユーザー名

`profiles` は既存マイグレーションで全ユーザーを補完し、新規ユーザー作成時にも自動作成される。そのため、ブロック一覧は `profiles` を1回取得し、見つからない場合だけ `Madoiユーザー` と表示する。`admin.auth.admin.getUserById` は使わない。

## DBと認可

新しいマイグレーションを1ファイル追加する。

- `list_owned_event_ids`
  - `security definer`
  - `auth.uid()` がNULLなら結果を返さない
  - 所有者IDを引数で受け取らない
  - 状態、カテゴリ、表示順、表示件数を許可値に正規化する
  - `event_ids uuid[]` と `total_count bigint` を返す
- `block_user_atomic`
  - `security definer`
  - 対象UUIDだけを引数で受け取る
  - 実行者は必ず `auth.uid()` から取得する
  - 自分自身と共通イベントのない相手を拒否する

どちらも `search_path = public` を固定し、`public` と `anon` から実行権限を外し、`authenticated` だけへ許可する。

一覧用に、所有者・カテゴリ・作成日時と、日程調整のイベントID・状態・確定日時を対象にした複合インデックスを追加する。既存インデックスと役割が重なる場合は、クエリで使う列を含む複合インデックスだけ追加する。

## エラー処理

- 一覧RPCが失敗した場合は、部分的な一覧を表示せずエラーとして扱う。
- RPC後のカード取得が失敗した場合も同様にエラーにする。
- ブロックRPCが失敗した場合は、関係データを一切変更しない。
- 存在しないプロフィールは一覧全体の失敗にせず、既定名で表示する。

## テスト

実装はテストを先に追加し、失敗を確認してから進める。

- マイグレーション検査
  - 一覧RPCが `auth.uid()` に限定されている
  - 空ページでも総件数を返す形になっている
  - ブロックRPCが登録と関係削除を同じ関数内で行う
  - 実行権限が `authenticated` に限定されている
- イベント一覧
  - RPCへ正しい状態、カテゴリ、表示順、表示件数、オフセットを渡す
  - RPCが返したIDだけを取得する
  - DBの返却順に依存せず、RPCのID順に表示する
  - 範囲外ページを最後のページへ補正する
  - 全履歴を500件ずつ取得する処理がなくなる
- ブロック
  - `blockUserAction` が原子的RPCを1回だけ呼ぶ
  - RPC失敗時は再検証しない
- ブロック一覧
  - プロフィール未取得時も既定名になる
  - `getUserById` を呼ばない
- 最終確認
  - 全テスト
  - ESLint
  - 本番ビルド

## 対象外

- eventsテーブルへの集計列追加
- トリガーによる一覧状態の事前計算
- Redisなど外部キャッシュの追加
- つながり一覧全体の検索・ページング
- UIデザインの変更

## 完了条件

- イベント一覧のアプリ転送量が、全履歴ではなく表示件数10〜50件に比例する
- 1000件を超えるイベントでも総件数とページングが正しい
- 現在の対応中・完了・中止の判定結果を維持する
- ブロック処理が部分成功しない
- ブロックユーザー数に比例した管理API呼び出しがない
- テスト、Lint、本番ビルドがすべて成功する
