# 参加者先行・Calendar集計型の日程調整 設計

日付: 2026-07-10
ステータス: 承認済み

## 目的

Madoiの日程調整を、候補を先に作って回答を集めるだけの流れから、参加者を集めて全員の空き時間を参考に候補を作る流れへ拡張する。

Google Calendarの予定名・場所・説明は、主催者にも他の参加者にも表示しない。空き状況は候補づくりの補助であり、参加意思の判断は従来どおり候補ごとの○△×投票で行う。

## 決定事項

- サイトはGoogleログイン必須にする。
- Calendar連携は日程調整へ参加・作成する条件にする。初回だけGoogleの認可画面で同意してもらう。
- 空き状況は名前なしの集計だけを表示する。個人ごとの可否や、予定の内容は出さない。
- 空き状況は15分単位で扱う。
- 空き状況はDBに保存しない。画面表示のためにGoogle Calendarから取得して、その場で集計する。
- 参加リンクに固定の有効期限は設けない。主催者が参加受付を閉じた時点でリンクを無効化する。誤送信時は主催者が停止・再発行できる。
- 参加受付を閉じてから候補作成へ進む。候補作成後に参加者を追加しない。
- 未ログインでの回答ページは廃止し、共有リンクを開いた人もGoogleログインへ進める。
- 投票後にCalendarの差分を監視・警告しない。候補を作る前と作成中にだけ最新の空き状況を使う。

## 利用の流れ

1. 主催者がイベントを作成する。
2. イベント画面で参加リンクをコピーして、参加者へ送る。
3. 参加者はリンクを開き、GoogleログインとCalendar連携を完了する。
4. イベント画面には `参加済み 3人` のように参加状況だけを表示する。
5. 主催者が `参加者を確定して日程調整へ進む` を押す。参加リンクはこの時点で閉じる。
6. 主催者は月カレンダーの濃淡を見ながら候補日時を作る。
7. 全参加者は候補ごとに○△×で投票する。
8. 主催者が投票結果を見て日程を確定し、Google Calendarの予定作成・参加者招待へ進む。

## 空き状況の取得と更新

### 表示内容

- 月カレンダーでは、空いている参加者が多い時間帯ほど見つけやすい濃淡で示す。
- 候補として選んだ時間帯には、`空き 3/5人` のような集計を表示する。
- 予定名、場所、説明、誰が空いているかは表示しない。
- `最終更新: 3分前` と手動の更新ボタンを表示する。

### 更新タイミング

- 調整カレンダーを開いたとき。
- 表示月を切り替えたとき。その月だけ取得する。
- 候補の開始・終了日時を変更したとき。
- 手動更新ボタンを押したとき。
- ブラウザのタブへ戻り、前回取得から5分以上経過しているとき。

Google Calendarの変更を即時通知で受け取る仕組みは、この変更には含めない。参加者ごとのWebhook監視と更新が必要になるため、初期版では画面表示時の取得を採用する。

## 画面と導線

### イベント詳細

- 参加状況、参加リンクのコピー、参加受付を閉じる操作を追加する。
- 参加受付中は日程調整作成を始められない。
- 参加受付を閉じると、候補作成画面へ進む導線を表示する。

### 参加リンク

- 新規ルートはイベント参加用の招待ページにする。
- 未ログインならGoogleログイン後に招待ページへ戻す。
- Calendar未連携なら連携完了後にイベント参加を確定する。
- 閉じたリンク、停止済みリンク、無効なリンクには日本語の案内を表示する。

### 候補作成

- 既存の候補日時ステップに、参加者全体の空き状況を集計した月カレンダーを追加する。
- 濃淡はあくまで参考情報であり、候補追加・削除、回答期限、リマインド、確認の既存ステップは残す。
- 候補作成開始時に、確定済みのイベント参加者を投票対象として作成する。主催者も参加者として投票できる。

### 回答・共有画面

- 回答はログイン済み参加者だけが行える。
- 参加者は自分のGoogle Calendarを見ながら、候補へ○△×を付ける。
- 既存の未ログイン回答リンクと公開清算リンクは、認証必須の導線へ置き換える。

## データ設計

### event_members

イベント単位の参加者を保持する。既存の `participants` は日程調整ごとの投票対象として残す。

主な項目:

- `event_id`
- `user_id`
- `display_name`
- `role` (`organizer` / `member`)
- `status` (`joined` / `removed`)
- `created_at`

イベント作成者は最初から `organizer` として登録する。参加受付を閉じた時点の `joined` メンバーを、日程調整作成時に `participants` へ複製する。

### event_invite_links

イベント参加リンクを保持する。

主な項目:

- `event_id`
- `token`
- `status` (`open` / `closed` / `revoked`)
- `created_by_user_id`
- `closed_at`
- `created_at`

固定の有効期限は持たせない。`closed` または `revoked` のリンクは参加に使えない。

### calendar_integrations

既存テーブルを継続利用する。トークンはユーザー本人のものとして保持し、空き状況の取得はサーバー側で必要な期間だけ実行する。

空き時間・予定あり時間は永続化しない。保存するのは連携トークン、認可情報、トークン期限だけとする。

## APIと権限制御

- イベント参加、参加受付の停止・再発行、候補作成はログイン済みユーザーだけが実行できる。
- 主催者だけがイベントの参加受付を閉じ、候補作成を始められる。
- 空き状況の集計APIは、イベント参加者であることを確認したうえで実行する。
- 集計APIのレスポンスには、個人を特定できるCalendar情報を含めない。
- Google Calendarからはfree/busy情報だけを使う。主催者のCalendarへ予定を作る既存機能と、確定後の参加者招待は維持する。

## 例外時の扱い

- Calendarの認可が失効・解除された参加者は、次の操作時に設定画面へ案内し、再連携後に参加を続けられる。
- 参加受付を閉じる時点で連携できない参加者がいる場合は、主催者に該当人数を案内し、再連携を待つか参加者から外すかを選ばせる。
- 空き状況取得に失敗した場合でも、候補日時を作る操作自体は止めない。失敗を明示し、更新ボタンで再取得できるようにする。
- 参加者が0人または主催者のみの場合も候補作成は可能にする。

## テスト方針

- `event_members` と `event_invite_links` の権限・状態遷移をテストする。
- 参加リンクがログイン・Calendar連携を経て参加へ至る導線をテストする。
- 集計値が個人名や予定内容を含まないことをテストする。
- 15分単位の濃淡計算、手動更新、5分経過後の再取得判定をテストする。
- 参加受付を閉じた後に、参加者スナップショットが投票対象へ引き継がれることをテストする。
- 既存の○△×投票、日程確定、Calendar予定作成、清算のテストを維持する。

## 実装しないこと

- Google CalendarのPush通知による即時同期。
- 予定のタイトル・場所・説明・参加者ごとの可否の表示。
- 自動で最適日時を確定する機能。
- 友達機能、再利用グループ、定期予定。
- 投票後のCalendar差分監視。

## 完了条件

- GoogleログインとCalendar連携を完了した人だけがイベントに参加できる。
- 主催者が参加受付を閉じるまで、参加リンクから参加できる。
- 候補作成時に、参加者全体の空き状況を15分単位・集計表示で確認できる。
- 空き状況に予定内容や個人を特定できる情報が含まれない。
- 参加者全員が○△×投票でき、主催者は既存の確定導線を使える。
- `npm.cmd test` と `npm.cmd run build` が通る。
