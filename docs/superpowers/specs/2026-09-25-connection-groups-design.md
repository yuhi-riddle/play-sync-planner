# つながりのグループ（自分だけの仕分け）と、つながり画面の役割の整理

- 日付: 2026-09-25
- ステータス: 設計確定（実装計画待ち）
- 比較シート: `design/proposals/2026-09-25-connection-groups-invite.html`（招待とのつなぎ方2案、案Aを採用）、`design/proposals/2026-09-25-connections-layout.html`（つながり画面の構成2案、案1を採用）
- 前段: `docs/superpowers/specs/2026-09-16-connections-active-events-design.md`（人ごとの「進行中の共通イベント」）

## 背景

つながり画面（`/connections`）が何のための画面か分かりにくい。

- 見た目は SNS の友だち管理（フォロー・お気に入り・ブロックの説明と、5つのタブ）だが、実際の用途は「次のイベントに誘う人を選ぶ」こと。フォローの効き目も「招待候補に出る」だけ
- お気に入りは「フォロー中の人を見つけやすくする目印」で、フォローとの違いが伝わりにくい
- 同じメンバーで複数のイベントや日程調整が並行しているとき、まとめて見る手段がない

## ゴール

- つながり画面を「よく遊ぶ仲間をまとめて、次のイベントに誘う場所」にする。開いてすぐ目的が伝わる
- 仲間ごとに、進めているイベントをまとめて見られる
- 招待のとき、いつものメンバーを一度に選べる

## 決定事項

| 項目 | 決定 |
|---|---|
| グループの性質 | 自分にしか見えない仕分け。相手には通知も表示もされない |
| 名前 | 1〜20文字。自分のグループ同士で同じ名前は不可 |
| 色 | 8色から選ぶ（下記）。並びの1番目を既定にする |
| 上限 | 1人20グループ、1グループ30人 |
| 入れられる人 | フォロー中か、一緒に参加したことがある人（今の招待候補と同じ範囲）。ブロック関係にある人は入れられない |
| フォローを外したとき | グループには残す |
| ブロックしたとき・されたとき | どちら向きでも、相手を自分のグループから外し、自分を相手のグループから外す。ブロックされたことは表示しない |
| 退会したとき | その人のグループを消し、ほかの人のグループからも外す。退会処理中（`deletion_state` が `active` 以外）の人も、入れられず、一覧にも出さない |
| グループの削除 | 画面内で確認してから消す。消えるのは仕分けだけで、フォローや参加履歴には影響しない |
| グループの並び | 作った順 |
| 人を入れる場所 | グループ画面の「メンバーを追加」と、人の行の「グループに入れる」の両方 |
| グループ画面の場所 | `/connections/groups/[groupId]` |
| グループ画面のイベント | メンバーが1人でも参加しているイベント。進行中はすべて、おわったもの（完了・中止）は最新5件を折りたたみで |
| 招待 | イベント詳細「Madoiで招待」の上にグループのボタンを並べ、押すとメンバーにまとめてチェックが入る（案A） |
| お気に入り | やめる。今のお気に入りは「お気に入り」という名前のグループへ移す |
| 招待候補の並び | 今のまま（サーバーからの並び）。お気に入りを先頭にする並べ替え関数 `sortInviteCandidates` は画面から使われていないので、PR④でお気に入りと一緒に消す |
| お気に入りの表と関数の削除 | 2段階。移行を本番で確かめたあとの別 PR で消す |

### 色

保存するのは色のキー。表示はカテゴリ色のトークンを使う（`design/tokens.css`）。並びは次の順で、1番目が既定。

`nazotoki` / `boardgame` / `travel` / `live` / `drinking` / `snowboard` / `movie_stage` / `honey`（`movie_stage` はカテゴリ定数と同じ綴り）

## 画面

### つながり画面（`/connections`、案1）

上から順に並べる。

1. ページ見出し「つながり」。説明文は「よく遊ぶ仲間をグループにまとめて、次のイベントにまとめて誘えます。」
2. 届いた招待（今のまま）
3. グループ: 見出しに「自分だけに見えます」を添える。各グループのカードに色・名前・人数・メンバー名・進めているイベントの件数を出し、押すとグループ画面へ。最後に「＋ グループを作る」。0件のときは作るボタンと一言の説明だけ
4. 人: タブは「一緒に参加／フォロー中／相互フォロー／ブロック中」。各行に所属グループ名を出し、操作は「グループに入れる／フォロー（解除）／ブロック」

「つながりの使い分け」の説明ブロック、お気に入りのタブとボタンはなくす。PC ではグループを左の列、人を右の列に置く。

「グループに入れる」は、自分のグループをチェックで選ぶ小さなパネルを開く。パネルの中で新しいグループも作れる。

### グループ画面（`/connections/groups/[groupId]`）

- 見出し: 色・名前・人数。名前と色の変更、グループの削除（画面内の確認つき）
- メンバー: 一覧と「外す」。「メンバーを追加」で候補から複数選んで入れる
- 進めているイベント: メンバーが1人でも参加している進行中のイベント。カードに「3人中2人」のような重なりと進行状態を出す
- 最近おわったイベント: 最新5件を折りたたみで
- 自分のものでないグループや存在しないグループの ID では 404

### 招待（イベント詳細「Madoiで招待」、案A）

- 候補一覧の上に「グループでまとめて選ぶ」として、グループのボタンを並べる。ボタンには、そのイベントにいま招待できる人数を出す（例「謎解き仲間 3人」）
- 押すと、グループのうち招待できる人にチェックが入る。参加済み・招待済みの人と、いま招待できない人（フォローを外していて、一緒に参加したこともない人）は除く。招待できる人が0人のボタンは押せない表示にする
- 候補は20件ずつ読み込むので、まだ読み込んでいない人にもチェックが入るようにする。チェックした人は一覧の先頭に出す
- 送信の仕組みは今のまま（`createEventUserInvitationsAction`）。ボタンの文言は選んだ人数を入れて「3人に招待を送る」
- グループを1つも作っていない人には、ボタンの行を出さない

## データ

### 表（新規）

- `connection_groups`: `id`、`owner_user_id`、`name`、`color`、`created_at`、`updated_at`。`(owner_user_id, name)` は一意。`name` は1〜20文字、`color` は上の8つのどれか
- `connection_group_members`: `group_id`、`member_user_id`、`created_at`。主キーは `(group_id, member_user_id)`

どちらも RLS で本人（グループの `owner_user_id`）だけが読み書きできるようにする。上限（20グループ・30人）と、入れられる人の条件は DB 側でも確かめる。読み書きは既存のつながり操作と同じく RPC 経由にし、同じ回数制限（`039_connection_action_rate_limit.sql` の方式）をかける。

### RPC（新規・変更）

- グループ一覧: 人数と、進めているイベントの件数を1回のクエリでまとめて返す（グループごとに問い合わせない）
- グループ画面: メンバーと、進行中のイベント（重なりの人数つき）、おわったイベント最新5件。`list_active_shared_events`（migration 050）を複数人に広げた形で、ブロック関係の人は数えない
- 作成・名前と色の変更・削除、メンバーの追加・削除、人の行から所属グループをまとめて設定
- 招待用: イベントとグループを受け取り、そのイベントにいま招待できるメンバーを返す
- 所属: 自分のグループの所属（グループ ID とメンバー）を一括で返す RPC を別に用意し、人の行の所属グループはこれで出す。`list_connections` には列を足さない
- `list_connections`・`get_connection_counts`: お気に入りの振り分けを外す（お気に入りの人も相互フォロー・フォロー中に出る）
- 一覧を読む RPC（グループ一覧の人数・名前・イベント件数、グループ画面のメンバー、所属、候補）は、ブロック関係の人と退会済み・退会処理中の人を除いて返す。同時操作で行が残っても画面には出ない
- `block_user_atomic`（migration 020）と退会の RPC（migration 045）: グループからも外す・消す処理を足す

### お気に入りの移行

- PR①のデプロイ直後に適用する migration（054）で、お気に入りが1人以上いる人ごとに「お気に入り」グループ（色は1番目）を作り、お気に入りの相手をメンバーに入れる。移行分は30人の上限を超えても入れる（上限は、あとから追加するときだけ効かせる） 退会済み・退会処理中の人は移さない。`list_connections`・`get_connection_counts` の振り分けの変更も同じ 054 で行う（先に入れると、デプロイまでの間お気に入りタブが空になるため）
- 同じ PR で、画面からお気に入り（タブ・ボタン・件数・説明）をなくす。`user_favorites` と `toggle_favorite_atomic`、各 RPC の `is_favorite` 列やお気に入りの分岐はこの時点では残す（画面からは使わない）
- PR④で、`user_favorites`・`toggle_favorite_atomic`・RPC のお気に入り関係の列と分岐・退会処理の該当行を消す。本番で移行後のグループが揃っていることを確かめてから出す

## PR の分け方

| PR | 中身 |
|---|---|
| ① | 表・RLS・RPC、お気に入りの移行 migration、つながり画面（案1）、グループの作成・編集・削除、人の行の「グループに入れる」、ブロック・退会の処理、招待候補の並べ替えの置き換え |
| ② | グループ画面のイベント（進行中＋おわった5件） |
| ③ | 招待のグループボタン |
| ④ | お気に入りの表・関数・列の削除 |

①のうち、グループ画面はメンバーの一覧と編集だけで出し、イベントの欄は②で足す。

## エッジケース

| 状況 | 挙動 |
|---|---|
| グループ数が20に達している | 「＋ グループを作る」を押せない表示にし、理由を出す |
| メンバーが30人に達している | 追加の候補を選べない表示にし、理由を出す |
| 名前が空・21文字以上・自分の別グループと同じ | 保存せず、理由を入力欄の下に出す |
| グループのメンバーを後からブロック（どちら向きでも） | グループから外れる |
| 移行した「お気に入り」グループが31人以上 | そのまま残す。追加だけできない |
| 他人のグループ ID で `/connections/groups/[groupId]` を開く | 404（存在を知らせない） |
| 招待でグループを押したが、全員参加済み | ボタンを押せない表示にし「全員参加済み」と出す |

## テスト

- DB（`tests/db/`）: RLS（他人のグループが読めない・書けない）、上限、名前の制約、入れられる人の条件、ブロック・退会での除去、お気に入りの移行、グループ一覧とイベントの RPC の結果
- ドメイン: 招待候補の並べ替え（グループの人が先頭）、招待できるメンバーの絞り込み
- 画面: つながり画面の構成（グループが人より上、お気に入りが出ないこと、0件のとき）、グループ画面、「グループに入れる」パネル、招待のグループボタン（まだ読み込んでいない人も選ばれる、参加済みを除く）

## 性能

- グループ一覧は1回の RPC で人数とイベント件数まで返し、グループごとの追加の問い合わせをしない
- グループ画面のおわったイベントは5件で打ち切る。進行中のイベントは件数の上限を設けないが、メンバー30人の範囲の参加イベントに限られる
- 人の行の所属グループは、所属を一括で返す RPC 1回で読み、行ごとに取りに行かない

## スコープ外

- グループを相手と共有する（全員が同じグループを見る）仕組み
- グループ画面から「このメンバーでイベントを作る」（案B）。グループ画面ができたあとに足せる
- 招待候補のサーバー側の並び順の変更
