# Madoi イベント詳細画面のタブ化 設計

日付: 2026-07-31  
ステータス: 承認済み

## 目的

イベント詳細画面（`/events/[eventId]`）は6ブロックの縦積みで、全ページ中もっとも縦に長く、DB往復も最多（16本前後）で、CLS も最悪（0.0816）だった。これをタブに分割し、開いた瞬間に見える情報を絞りつつ、初回表示に必要なデータ取得を減らす。

見やすさと速度の両方を目的とする。表示を畳むだけでなく、**タブを開くまでそのタブのデータを取りに行かない**ところまでを対象に含める。

## 対象

- イベント詳細画面のタブ構成とヘッダー要約
- タブ状態の URL 反映
- タブ単位のデータ取得分割
- 読み込み中表示（`loading.tsx`）のタブバー固定

## 画面構成

### ヘッダー（タブの外・常時表示）

- イベント名
- 進行状況の要約: 状態バッジ（参加者募集中 / 日程調整中 / 確定）、参加人数、回答期限または確定日時
- 「日程調整を始める」ボタン（オーナーかつ参加受付が `closed` のときのみ）

状態バッジは既存の判定をそのまま使う（`status === "confirmed"` なら確定、日程調整が1件以上あれば日程調整中、どちらでもなければ参加者募集中）。日時は join 済みの日程調整リストから引く。**日程調整が複数ある場合は、確定済みがあればその `confirmed_start_at`、なければ `answer_deadline_at` が最も近いものを表示する**。日程調整が1件もなければ日時は表示しない。

進行状況をヘッダーへ出すことで、どのタブを開いていてもイベントの状態が分かる。これにより日程調整の一覧を常時表示する必要がなくなり、タブを4つに抑えられる。

### タブ

| タブ | `tab` の値 | 中身 |
|---|---|---|
| 概要 | `overview`（既定） | 日程調整リスト → イベント情報（カテゴリ・場所メモ・URL・メモ・経路リンク）→ 編集 / 中止 / このメンバーでもう一度 |
| 参加者 | `members` | オーナー: 招待リンク管理＋つながりから招待 / 非オーナー: 参加人数 |
| チャット | `chat` | 既存の `EventChat` をそのまま移設 |
| タスク | `tasks` | 既存の `EventTaskList` をそのまま移設 |

タブの外・最下部に「イベント一覧へ」を残す。

### 検討して見送った案

- **全ブロックを5タブに分ける案**: 日程調整に専用タブを与えると、スマートフォン幅でタブ1つあたり約70pxとなり文字が詰まる。日程調整の一覧は多くて1〜2件と軽いため、概要タブの先頭に置く方が収まりが良い。
- **イベント情報と日程調整をタブの外に常時表示する案**: 縦の長さが減らず、タブ化の効果が薄れる。ヘッダー要約で進行状況が分かるため、常時表示する必要がない。

## URL と遷移

- `/events/[eventId]?tab=overview|members|chat|tasks`
- `tab` 未指定および不正値は `overview` にフォールバックする
- タブはサーバーコンポーネントのまま `<Link>` で遷移する
- **タブのリンクは `prefetch={false}` とする**。middleware が全リクエストで Supabase に2往復しているため、4タブ分を先読みすると往復が8本増え、タブ化で削減した分を相殺してしまう

タブ値のパースは純関数として `lib/domain/event-tabs.ts` に切り出し、単体テストの対象とする（`lib/domain/cls.ts` と同じ方針）。

## データ取得の分割

### 現状

```
波1: events（plans を join）                                    1本
波2: 参加人数 / 招待リンク / ログインユーザーID（並列）             3本
波3: 招待候補 / チャット / タスク（並列、各々が内部で複数本を直列）
```

`loadEventChat` は「自分が参加者か」の判定・メッセージ取得・投稿者名の解決を**3本直列**で実行しており、そのうち後半2本は概要タブでは不要である。

### 変更後

**常に取得する（5本・3波）**

1. イベント本体（日程調整リストを join）
2. 参加人数 / ログインユーザーID / 招待リンクの状態 — 3本を並列で取得。招待リンクの状態は「日程調整を始める」ボタンの出し分けに使うため、参加者タブ以外でも必要
3. **自分が参加者かどうか** — ログインユーザーIDが確定してから引くのでこの波になる。概要の「このメンバーでもう一度」、タスクの編集可否、チャットの投稿可否すべてに効くため常時必要

**タブごとに追加で取得する**

| タブ | 追加取得 |
|---|---|
| 概要 | なし |
| 参加者 | 招待候補（オーナーのときのみ） |
| チャット | メッセージ全件＋投稿者名の解決 |
| タスク | タスク一覧＋担当者候補 |

`loadEventChat` を「参加判定」と「メッセージ取得」に分割する。参加判定は常時実行し、メッセージ取得はチャットタブでのみ実行する。

これにより概要タブ表示時の往復は16本前後から5本程度になる。

## 読み込み中表示

`app/events/[eventId]/loading.tsx` は現在ページ全体のスケルトンだが、**ヘッダーとタブバーは実物と同じ位置・同じ高さで描画する**。タブを切り替えたとき、バーは動かず中身だけが差し替わる形にして、切り替えのたびにレイアウトがずれないようにする。

## テスト

`tests/` 直下に置く（このプロジェクトはコロケーション不可）。

- タブ値のパース: 既定値へのフォールバック、不正値の扱い（純関数の単体テスト）
- タブごとの出し分け: `tab=chat` でチャットが表示され、タスクが表示されないこと
- 非オーナーで参加者タブを開いたときの表示
- ヘッダー要約の状態別表示（参加者募集中 / 日程調整中 / 確定）
- **概要タブではチャットのメッセージを取得しないこと** — 今回の速度改善の核なので、取得関数の呼び出し有無で検証する
- 既存のイベント詳細画面まわりのテストが通ること

## 今回やらないこと

- **参加者の一覧表示**。現状も人数のみのため、非オーナーの参加者タブは人数だけになる。一覧表示は新機能として別途扱う
- 未読バッジ
- チャットのリアルタイム更新
- middleware の `user_consents` チェックを `user_metadata` へ移す件（速度改善の別項目として保留中）
