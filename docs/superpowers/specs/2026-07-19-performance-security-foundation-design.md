# Madoi 性能・セキュリティ基盤強化 設計

日付: 2026-07-19
状態: 承認済み

## 1. 結論

画面側だけを軽くするのではなく、DBの権限境界と取得量から直す。

つながり、カレンダー、イベント詳細は、ログイン中の利用者をDB側で特定する用途別RPCとRLSへ移す。Next.jsは初回表示に必要な少量データだけを取得し、残りをページングまたは遅延読み込みする。管理権限クライアントはCron、公開共有リンクの限定処理、Googleトークン更新など、RLSを越える必要がある処理に限る。

セキュリティ強化は利用者の操作を増やさない。CSP、入力検証、回数制限、最小権限、監査ログを画面の裏側に置く。

## 2. 成功条件

### 性能

- 低性能スマートフォン相当、4倍CPU低速化、低速4G相当で、主要部分を3秒以内に操作できる。
- 3秒は全件取得の完了時間ではない。初回表示後のデータは操作に応じて追加取得する。
- DBの一覧RPCは、代表的な大量データで1秒以内を目標とする。
- 一覧は1回20件を上限とする。メッセージだけは1回50件とする。
- Google Calendarが遅い場合も、Madoiの予定は先に操作できる。

### セキュリティ

- 利用者に追加のログインや確認操作を求めない。
- 未認証利用者は保護RPCを実行できない。
- ログイン利用者は、URLや引数を変更しても他人のデータを取得・更新できない。
- 管理権限クライアントを通常画面の取得経路から外す。
- 高コスト操作と公開リンク操作へ回数制限を設ける。
- ブラウザへ返すエラー、ログ、監査記録に秘密値を含めない。

## 3. 現状と問題

### 3.1 性能

- `/connections` は、参加イベントと各イベントの参加者を広く取得してから、アプリ側で候補者を組み立てている。
- `/plans` は、参加イベントに属する日程、候補日、回答を表示月に限定せず取得している。
- `/events/[eventId]` は、概要表示と同時に招待候補を作るため、共有イベントと参加者を広く走査している。
- イベントチャットは直近50件へ制限済みだが、過去メッセージを取得するページングがない。
- 重い部分を分離する`loading.tsx`または`Suspense`境界がない。
- 実利用環境で3秒基準を継続確認する計測がない。

### 3.2 セキュリティ

- 利用者向け画面とServer Actionで`createSupabaseAdminClient`が広く使われ、RLSを迂回している。アプリ側の所有者確認が1か所抜けると、DBが最後の防壁にならない。
- `next.config.ts`にCSPなどの主要セキュリティヘッダーがない。
- チャット、Google空き状況、公開回答、公開支払い記録などに回数制限がない。
- 本番Cronは`CRON_SECRET`がない場合、`User-Agent: vercel-cron/1.0`だけで認証する。この値は外部から送信できる。
- 既存の保護関数は`PUBLIC`から実行権限を外しているが、`anon`を明示的に外していない。

2026-07-19に本番の公開用`anon`キーから架空UUIDだけを使って確認したところ、次の関数がHTTP 200で実行された。

- `is_event_owner`
- `is_joined_event_member`
- `have_shared_event`
- `is_user_blocked`
- `is_following`
- `list_owned_event_ids`

架空UUIDでは結果が`false`または空配列になるため、確認中のデータ変更や実データ取得はない。ただし、引数に利用者IDを受け取る関係判定関数は、実在IDを指定すると関係の有無を推測できる。匿名実行権限の除去を実装の最初に行う。

## 4. 対象範囲

### 対象

- つながり一覧の分類別ページング
- カレンダーの表示月限定取得
- イベント詳細の段階表示
- 招待候補とメッセージのページング
- 管理権限クライアントの縮小
- DB関数、RLS、関数実行権限の整理
- 認証済み操作と公開リンク操作の回数制限
- CSPと主要セキュリティヘッダー
- Cron認証の必須化
- 重要操作の監査ログ
- Core Web Vitalsとサーバー処理時間の少量計測
- 大量データ、権限、公開手順の自動テスト

### 対象外

- 個別チャット
- グループチャットの画像・ファイル添付
- お金の横断集計画面
- Redis、外部ジョブキュー、外部WAF
- Google以外のログイン、Google以外のカレンダー連携
- 利用者へMFAまたは短時間の再ログインを求める変更

対象外の機能は、この設計で整えるページング、回数制限、監査ログを再利用して後続仕様で追加する。

## 5. 全体構成

```text
ブラウザ
  ↓ ページ、月、イベントID、カーソルだけを送る
Next.js Server Component / Server Action / Route Handler
  ↓ ログインセッション、入力検証、回数制限
Supabase authenticated client
  ↓ security invoker RPC またはRLS付きテーブル操作
PostgreSQL
  ↓ auth.uid()、固定上限、索引
利用者が閲覧できる少量データだけを返す
```

通常の画面表示と更新は、利用者本人のSupabaseセッションで行う。所有者IDや利用者IDをクライアントから受け取り、その値を信用する設計にはしない。

`security invoker`を標準とする。複数テーブルを1トランザクションで変更するなど、RLSを越える必要がある関数だけ`security definer`を使う。その場合は、次を必須とする。

- `search_path = ''`
- テーブル、関数、型をスキーマ付きで参照
- `auth.uid()`がNULLなら拒否
- 実行者IDを引数で受け取らない
- 動的SQLを使わない
- 件数、期間、状態の入力を許可値へ正規化
- `PUBLIC`と`anon`から実行権限を外し、必要なロールだけへ明示許可

## 6. 画面ごとのデータフロー

### 6.1 つながり

初回表示では、各分類の件数と選択中分類の先頭20件だけを取得する。

分類は次の5種類を維持する。

- お気に入り
- 相互フォロー
- フォロー中
- 一緒に参加
- ブロック中

分類変更時に対象分類の先頭20件を取得する。追加表示は、最終行の並び順と利用者IDから作るカーソルを渡す。オフセットは深いページほど遅くなるため使わない。

DBは、ログイン利用者が参加したイベント、フォロー、ブロック、お気に入りだけを基に候補を組み立てる。表示名は`profiles`から一括解決する。アプリ側でイベントごとの参加者全件を組み立てない。

### 6.2 カレンダー

Madoiの予定は、表示月とカレンダー表示に必要な前後日だけ取得する。参加イベント全体の日程、候補日、回答は取得しない。

表示順は次のとおりとする。

1. カレンダー枠とMadoiの予定
2. Google Calendarの読み込み状態
3. Google Calendarの予定

Google APIには5秒のタイムアウトを設ける。失敗またはタイムアウト時は、Madoiの予定を保持したまま再試行を表示する。前月と翌月は月移動時に取得する。

### 6.3 イベント詳細

最初に次だけを表示する。

- イベント概要
- ログイン利用者の参加状態と権限
- 参加人数
- 直近の予定

チャットは直近50件を別境界で読み込む。過去分は作成日時とIDのカーソルで50件ずつ取得する。

招待候補は主催者が招待欄を開いた時だけ取得する。1回20件とし、候補検索、関係判定、ブロック判定をDBで行う。イベント概要の表示を招待候補検索で待たせない。

### 6.4 表示と失敗

- 画面全体を1つのローディング表示にしない。
- 概要、一覧、Google予定、チャット、招待候補を独立した`Suspense`境界にする。
- 追加取得に失敗しても表示済みデータを消さない。
- 読み込み中、空、再試行、回数制限を対象領域内に表示する。
- RPCがない場合や権限が不正な場合、管理権限経路へ自動で戻さない。

## 7. DBと権限

DB変更は役割ごとに分ける。番号は既存の`020`に続ける。

### 7.1 `021_function_privilege_hardening.sql`

- 既存関数の実行権限を一覧化する。
- 保護関数について`PUBLIC`、`anon`の実行権限を明示的に外す。
- ポリシー専用の`security definer`補助関数を非公開`private`スキーマへ移す。
- 公開RPCは`security invoker`を優先する。
- `security definer`を残す関数は空の`search_path`とスキーマ付き参照へ変更する。
- `anon`、`authenticated`、`service_role`相当の権限テストを追加する。
- 今後の関数が暗黙に公開されないよう、既定実行権限を取り消す。既存関数への必要な許可を同じマイグレーションで明示する。

補助関数の移動は1トランザクションで行う。先に`private`スキーマへ代替関数を作成し、RLSポリシーの参照先を変更し、権限テストを通してから公開スキーマの旧関数を削除する。ポリシーから呼ぶ関数には必要な`USAGE`と`EXECUTE`だけを許可するが、`private`スキーマ自体はData APIの公開対象にしない。アプリから既存の関係判定関数を直接呼ぶ処理は、用途別の公開RPCへ置き換える。

最初の本番確認では、`anon`から対象関数を呼び、HTTP 401または403になることを実測する。関数の存在だけを見る画面確認では完了としない。

### 7.2 `022_page_query_performance.sql`

次の用途別RPCと索引を追加する。名前と引数は実装計画で型まで固定する。

- つながり分類ごとの件数
- つながり分類のカーソルページ
- 表示月のMadoi予定
- イベント招待候補のカーソルページ

既存索引を調べ、同じ先頭列の索引を重複作成しない。追加候補は次の検索経路を基準にする。

- `event_members(user_id, status, event_id)`
- `event_members(event_id, status, user_id)`
- `plans(event_id, status, confirmed_start_at)`
- `candidate_dates(plan_id, start_at)`
- `user_connections(follower_user_id, followed_user_id)`と逆方向
- `event_messages(event_id, created_at desc, id desc)`

RPCは最大件数を内部で固定する。呼び出し側が大きな`limit`を渡しても20件、メッセージは50件を超えない。

### 7.3 `023_rate_limits_and_security_audit.sql`

回数制限と監査ログは`private`スキーマに置き、Data APIから直接取得できないようにする。

回数制限は固定時間窓とし、次を初期値とする。

| 操作 | 単位 | 上限 |
|---|---|---:|
| チャット投稿 | 利用者 | 20回/60秒 |
| Google空き状況取得 | 利用者 | 6回/60秒 |
| フォロー、招待、ブロック | 利用者 | 30回/60秒 |
| イベント、日程、プロフィール更新 | 利用者 | 30回/60秒 |
| 公開回答、公開支払い記録 | 共有リンクのHMAC | 10回/60秒 |

公開リンクの識別にはサーバー秘密値を使ったHMACを用いる。URLトークン、IPアドレス、メールアドレスを回数制限テーブルへ保存しない。超過時はHTTP 429と再試行可能時刻を返す。

監査ログは次の操作を対象にする。

- ブロックと解除
- イベント招待の作成、承認、拒否、取消
- 公開支払い記録と受取確認
- Google Calendar連携と解除
- 回数制限による拒否

記録項目は、実行者ID、操作名、対象種別、対象ID、成功・拒否、作成日時とする。本文、URLトークン、Googleトークン、Cookie、IPアドレスは記録しない。90日を過ぎた記録は認証済みCronで削除する。

Cron認証失敗は、攻撃者による大量書き込みを避けるためDB監査ログへ保存しない。秘密値を含まない構造化サーバーログとして記録し、同じデプロイ内で出力量を制限する。

### 7.4 `024_performance_measurements.sql`

Core Web Vitalsの少量サンプルを保存する非公開テーブルを追加する。保存項目は画面テンプレート、指標名、値、端末区分、作成日時に限る。利用者ID、完全なURL、クエリ文字列、イベントID、共有トークンは列として持たない。30日を過ぎた記録は認証済みCronで削除する。

## 8. 管理権限クライアント

`createSupabaseAdminClient`の利用箇所をテストで一覧化し、許可リスト方式にする。

残してよい用途は次に限る。

- 認証済みCron
- 公開共有リンクのトークン検証後に必要な限定処理
- Google Calendarトークンの暗号化更新
- 公開リンク用回数制限のHMAC記録
- RLSでは表現できない管理処理を行う、入力と所有者確認済みの小さな関数

一覧画面、イベント詳細の通常表示、ログイン利用者の通常更新では使わない。管理権限が必要な処理は関数へ閉じ込め、取得した管理クライアントを広い関数へ渡さない。

## 9. Next.jsの入口防御

### 9.1 共通ガード

Server ActionとRoute Handlerで次を共通化する。

- ログイン必須
- UUID、年月、カーソル、列挙値のZod検証
- 所有者または参加者権限の確認
- 回数制限
- 外部向けエラーの一般化
- 内部ログから秘密値を除去

認証だけで認可を済ませない。イベントID、日程ID、招待IDなどの対象ごとに所有者または参加者を確認する。

### 9.2 セキュリティヘッダー

Middlewareでリクエストごとのnonceを生成し、CSPを付ける。許可先は実際に使うSupabase、Googleプロフィール画像、Google Calendar通信に限定する。

CSPに加えて次を付ける。

- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy`で未使用のカメラ、マイクなどを無効化
- `frame-ancestors 'none'`
- `object-src 'none'`
- `base-uri 'self'`

プレビュー環境で違反を確認して許可先を確定し、main反映前に強制CSPへ切り替える。`unsafe-eval`は開発環境だけに限る。

### 9.3 Cron

本番では`CRON_SECRET`を必須とする。値が未設定なら常に401を返す。`User-Agent`だけの認証は廃止する。通知作成は既存の重複防止キーを維持し、同じCronが複数回届いても結果が増殖しないようにする。

## 10. 計測

### 10.1 ブラウザ

`useReportWebVitals`でLCP、INP、CLSを少量サンプリングする。保存するのは画面テンプレート、指標名、値、端末区分、作成日時だけとする。利用者ID、URLクエリ、イベントID、共有トークンは保存しない。保持期間は30日とする。

計測受付APIにも回数制限と入力上限を設ける。画面テンプレートはサーバー側の許可リストから選び、クライアントが送った任意文字列をそのまま保存しない。

### 10.2 サーバーとDB

- 用途別RPCの処理時間を`Server-Timing`または構造化ログへ出す。
- DBエラーはコードと処理名だけを残し、SQL引数と行データは残さない。
- 遅いRPCは`EXPLAIN (ANALYZE, BUFFERS)`で索引利用を確認する。
- 1回の返却行数が上限を超えないことを自動テストする。

性能計測自体が負荷にならないよう、ブラウザ計測は最大5%にする。

## 11. テスト

### 11.1 大量データ

本番ではなく、隔離したローカルまたは検証用DBへ次のデータを生成する。

本番接続値が入った`.env.local`を大量データ試験へ使わない。試験コマンドは接続先がlocalhostまたは明示した検証プロジェクトでなければ停止する。

- 所有イベント1万件
- つながり候補5千人
- 日程、候補日、回答を合計1万件以上
- 1イベントのメッセージ1万件

確認項目は次のとおり。

- 初回RPCが固定件数だけを返す。
- 深いページでもカーソルにより応答時間が大きく悪化しない。
- 月変更前に別月の候補日と回答を取得しない。
- 招待欄を開く前に候補検索を実行しない。
- 低速4Gと4倍CPU低速化で主要部分が3秒以内に操作可能になる。
- DB RPCの代表実行が1秒以内になる。

### 11.2 権限

- `anon`は保護RPCを実行できない。
- 利用者Aは利用者Bのイベント、つながり、カレンダー、招待候補を取得できない。
- 所有者以外は招待候補を取得できない。
- 非参加者はイベントメッセージを取得・投稿できない。
- 上限を超えた操作は429になり、DB更新を行わない。
- `CRON_SECRET`なし、誤値、正値をそれぞれ確認する。
- CSP、画像、Google OAuth、Google Calendar通信が共存する。
- 監査ログに本文、トークン、Cookie、IPアドレスが入らない。

### 11.3 回帰

- 既存の単体テスト、Lint、型検査、本番ビルドをすべて通す。
- Googleログイン、Google Calendar連携、共有回答、清算、通知を確認する。
- 320px、375px、390px相当の画面幅で固定下部ナビと追加読み込みを確認する。

## 12. 公開手順

1. 現在の取得件数、処理時間、管理権限クライアント利用箇所を記録する。
2. `021`を本番DBへ適用し、匿名実行が401または403になることを実測する。
3. `022`、`023`、`024`を適用し、RPCの戻り値、件数上限、回数制限、監査ログ、計測データの非識別性を実測する。
4. アプリをVercelプレビューへ公開する。
5. 大量データ、低速条件、権限、CSP、Google連携を確認する。
6. すべて成功した場合だけmainへ反映する。
7. 本番RPC、Vercelデプロイ、公開URL、ログイン後主要画面の順に確認する。

DB変更は追加型とし、既存データと旧テーブルを削除しない。問題が出た場合はアプリを前版へ戻せる。新RPCがない場合に管理権限経路へ戻す互換処理は作らない。

## 13. 完了条件

- 本番の`anon`から保護RPCを実行できない。
- つながりは分類別20件、カレンダーは表示月、招待候補は開いた時だけ20件を取得する。
- イベントチャットの過去分を50件ずつ追加取得できる。
- 通常画面の管理権限クライアント利用が許可リスト外に残っていない。
- 回数制限、監査ログ、CSP、Cron秘密値必須化が機能する。
- 大量データ条件でDB応答1秒以内、主要部分3秒以内の基準を満たす。
- 追加取得の失敗時に表示済みデータを保持する。
- 全テスト、Lint、型検査、本番ビルドが成功する。
- DB先行、プレビュー確認、本番確認の順序を記録できる。
